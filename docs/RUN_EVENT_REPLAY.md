# SIE-017 run replay and controls

The API can mount injected run services at `GET /v1/runs/:runId/events`, `GET /v1/runs/:runId`, `POST /v1/runs/:runId/cancel` and `POST /v1/runs/:runId/retry`. They require an authenticated Academy or Command session, a tenant UUID and an explicitly authorized origin. The durable service verifies project membership before reading or changing a run.

Clients resume event history with the standard `Last-Event-ID` header or the `after` query parameter. The bounded response emits durable event IDs in order and finishes with a `replay-end` cursor. `EngineClient.replayRunEvents` validates scope and SSE framing; `inspectRun`, `cancelRun` and `retryRun` expose explicit credentialed controls without automatic retries.

Cancellation stops only local, non-dispatched work. Provider-linked, dispatched or reconciliation work returns `provider_cancel_unavailable`; the API never claims that an external provider stopped. Retry requires a caller idempotency key and remains limited to the zero-cost read jobs accepted by the durable service. Billable or provider-linked work fails closed.

All routes are disabled unless a trusted runtime injects authentication and durable storage. When that service also provides `subscribe`, the route establishes the subscription before querying durable history, buffers events that arrive during replay, deduplicates by durable event ID and leaves the SSE response open for live updates. Disconnecting or a stream error releases the subscription. Without `subscribe`, the endpoint preserves the finite replay response.\n\nThe injected subscriber must authorize the same tenant, run and identity scope and publish monotonically increasing durable event IDs. This increment does not provide a production message broker, provider cancellation guarantees, production deployment or browser acceptance; those remain required before SIE-017 is complete.
